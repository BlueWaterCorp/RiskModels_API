# RiskModels API — Data Issues Digest

_Running list of API / SDK discrepancies found while wiring the 13F portfolio
toolkit. Newest first. Last updated 2026-10-02 (riskmodels-py 0.3.11 / in-tree 0.4.0)._

### Added 2026-10-02 (PR #373 review, second pass — findings 4–9 resolved)

All six are method/hygiene items in OUR code. Each is pinned by a hermetic test
(`tests/test_review_pass2.py`, `tests/test_hedge_sign.py`); none moves a published number.

- **🟢 F4 — the gates are now controls, not constants.** `build_lagged` had `GATE_*` and `gate_verdict` but nothing called them; stages 1–2 ran regardless, and the layer bar was a literal `50` in three files. Now: `gate_verdict` (Stage 0, on the **mean** |diff|), `layer_gate_verdict` (Stage 2, on each layer's **median** |diff| < `LAYER_GATE_MEDIAN_BPS`), `stage0_summary`, and `enforce_gate` which raises `GateStop`. The CLI refuses stages 1–2 after a STOP unless `--force` (diagnostics only). `reaudit_berkshire.py`, `run_pershing.py`, `deshaw_report_date.py`, `deshaw_analyze.py` all route through these. Two gates, two statistics, deliberately: the Stage 0 mean penalises the tail quarters where a rebuild diverges most; the layer median asks whether the typical quarter's attribution reproduces given the gross already passed.
- **🟢 F5 — the terminal row is detected by property.** It was `portfolio_rows(name)[-1]` *after* null-gross rows were filtered — wrong the moment the endpoint's last row has a null gross. Now `terminal_teo(name)` = max teo of the **raw** endpoint series, and `stage0` tags/drops it. **Note:** the other property Conrad suggested — "forward quarter not complete in the calendar" — does **not** fire for this defect (the SPY calendar runs to 2026-07-24, past every filer's last quarter end), and a market-vs-SPY deviation threshold at 5× the filer median catches COVID-era quarters for every filer. The raw-max-teo rule is the one that matches the defect mechanism; the implied-horizon check in `reaudit_berkshire.py` stays as the *evidence* the row is defective. Replaced five positional picks; all five filers' terminal teos are unchanged, so no number moved.
- **🟡 F6 — the 1,000-row holdings cap, quantified; basis now stated.** `get_filer_holdings(limit=1000)` returns the top 1,000 rows by weight and the SDK offers no paging. From the cached records (`n_total_holdings` / returned weights): **71 of 74 D. E. Shaw books are truncated; the unlisted tail is a median 0.4% of book weight, max 3.2%.** The endpoint's weights are weights of the FULL book (they sum to <1 when truncated), so `covered_w` from `portfolio_window_return` was already an absolute share of the book and the tail was uncovered by construction — but it never appeared in `missing`, and `deshaw_size_control.py` divided by the sum of *returned* weights, measuring coverage of the top-1,000 rows instead. Now `book_truncation(rec)` reports the tail, Stage 0 records carry `book_*` fields, and the size control reports coverage on the absolute basis with `book_tail_w_median` alongside. Every coverage figure in the documents now says which basis it is on.
- **🟢 F7 — layers carry coverage, and the imputation is named.** `portfolio_window_layers` now returns `covered_w` and `n_names` with the four layers; Stage 2 records carry `layer_covered_w`. Renormalising to covered names assigns the covered book's return to the uncovered weight — that is an **imputation**, defensible for a partial universe, but the PR's "never a silent fill" wording overstated it and is corrected. Coverage is stated on every published figure instead.
- **🟡 F8 — NaN-day drop ≡ zero return; a NaN TAIL truncates the loss.** Dropping a NaN day before compounding is right when the vendor's next print spans the gap. It is wrong for a delisting without a terminal print: the name compounds over its printed days only and still counts as covered, so the post-delisting loss is never seen. Documented in `window_return`'s docstring and pinned as *behaviour* (not fixed) by `test_nan_tail_truncates_the_loss_documented_behaviour`.
- **🟡 F9 — hedge sign convention single-sourced; NOT flipped.** `decompose()["hedge"]` is now converted to a short ratio by exactly one function, `hedge_short_ratio`, under one flag `HEDGE_IS_SHORT_RATIO`, used by `market_neutral_overlay`, `compute_overlays` and `charts_raw_vs_hedged`. The flag stays `True` (the convention the July realized-beta charts were validated on) because on 2026-09-22 the live API returned **mixed signs across names** — SPY *positive* for AXP/KO/BAC, *negative* for NVDA, sector/subsector negative throughout — so neither the SDK-documented `hedge == -hr` nor the overlay's reading could be confirmed empirically. When the vendor settles it, the fix is the flag; five hermetic tests pin the behaviour either way. A name whose `decompose()` has no hedge block (the AAPL case) is now reported in `MarketNeutralOverlay.unhedged_tickers` instead of being silently renormalised away. D.8.57 remains open on the vendor side.

### Added 2026-09-22 (live API — hedge sign flipped, and AAPL returns no hedge at all)

Both found while re-running the suite after the review fixes. **Neither is caused by our
changes** and neither is patched in this pass — the overlay correction is second-pass work
(finding 9 / D.8.57).

- **🔴 `decompose()["hedge"]` has flipped sign against the live API.** The overlay was built on
  the convention that `hedge[etf]` is a **positive per-dollar SHORT ratio**, so a long-only 13F
  book yields a positive SPY notional. Today the identical code path returns SPY **negative**.
  **Evidence it is a behaviour change, not a regression we introduced:** `charts/overlay_data.json`
  (built July) records Berkshire `etf_shorts["SPY"] = +44,722,536`; the same construction on
  2026-09-22 returns ≈ **−1.5e10**. The sign reversed. (The magnitude gap is the separate,
  already-documented `adj_mv` 1000× scale bug, not part of this finding.) **The live API now
  agrees with its own documentation** — the SDK docstring and `sdk/tests/test_decompose.py`
  fixture have always said `hedge[etf] == -hr` — so **our overlay is the side that is out of
  step.** Consequence: every overlay number in this repo (beta reductions Pershing 96–103%,
  Appaloosa 96–110%, Berkshire 76–88%) was measured in July under the old sign and **does not
  reproduce today without flipping it.** The fix is one line; re-deriving and re-validating the
  published figures is not, which is why it is scheduled rather than slipped in. The live
  overlay test is `xfail(strict=False)` with the full rationale in its docstring, so it flips
  back to green automatically if either side is corrected.
- **🔴 `decompose("AAPL")` returns an EMPTY hedge dict and null exposures.** `hedge = {}`, every
  `exposure.*.hr` / `.er` is `None`, and `_data_health.er_populated = False` — while AXP, KO,
  NVDA, MSFT and BAC all return three populated legs on the same call, same `data_as_of`
  (2026-09-22). This is a **per-ticker coverage gap, not a global outage.** It matters
  disproportionately because **AAPL is Berkshire's largest position**, so any bottom-up overlay
  built today silently drops the single biggest name and renormalises around it without
  erroring. Anything consuming `decompose()` should treat an empty `hedge` as a hard failure for
  that name rather than a zero exposure.
- **🟡 Neither issue touches the lag study.** Strand A and Strand B run off
  `get_returns_decomposition`, `get_ticker_returns` and `get_filer_*` — not `decompose()` — so no
  Berkshire or D. E. Shaw figure in FINDINGS.md depends on either. The blast radius is the
  market-neutral overlay work only.

### Added 2026-09-22 (PR #373 review — three method defects, all found by Conrad in source)

These are OUR defects, not the vendor's. Recording them here because two of the three are the
same *class* of error as the NaN bug: a quantity that looked plausible flowing through a step
that never checked it against an independent reference.

- **🔴 Trading-day offsets were conflated with calendar days, so the "commercial window" was never measured.** `deshaw_report_date.WINDOWS` defined every window as a **trading-day** offset from quarter end, but the book goes public at **calendar** teo+45 — a median of **32 trading days** (range 30–33, n=51). The old D (+35..+45) and E (+45..+55) report-anchored windows were therefore *both already post-public*, with E sitting **13–23 trading days after disclosure** while the writeup described it as "the 10 days after the ~45-day filing". **Fix:** windows now carry an anchor basis (`report` or `entry`); D and E are anchored at `build_lagged.entry_date(teo)`. **Effect:** the post-public window goes from −7 bps / t=−0.10 ("a coin flip") to **+75 bps / t=1.46**, its regression alpha from +34 bps t=1.88 to **+20.5 bps t=1.17** (further from significance), and the size-matched placebo comparison flips to **−37 bps t=−1.87**. The *conclusion* — nothing bankable survives to disclosure — is unchanged on all three measures. Windows A/B/C, the same-quarter control and the A regressions are report-anchored and unaffected.
- **🟡 Look-ahead was possible for late-filed books (latent; did not bite for Berkshire).** `holdings_for_teo` escalates `as_of` to teo+90/+120 when the tight teo+55 buffer returns the prior book — i.e. it accepts filings made *after* teo+55 — but `stage1` entered every book at `entry_date(teo)` = teo+45 regardless. **Fix:** `lagged_entry()` floors entry at the book's provably-public date (`book_public_date()`: the record's `filing_date`, and `as_of_requested` whenever the fetch had to escalate past teo+55). **Effect: zero.** All 43 Berkshire books return at the teo+55 buffer and none has a `filing_date` after its entry, so **0 of 42 windows are floored and no Berkshire figure moves.** It would bite elsewhere: **Pershing has 10 of 77 books escalating past teo+55** and 3 whose entry preceded the recorded filing date by up to 61 days. Fixed defensively so the next filer does not inherit it.
- **🔴 Two gross Sharpes were quoted on different bases.** The Stage 1 headline series was fed to `stats()` **unnormalised** while the Stage 2 layer series was divided by `q_len` first — and `stats()` annualises with `n/4` years, which assumes every window is exactly one quarter. **Six of the 42 Berkshire windows span ~2 quarters and one spans 3** (a book held across a missing quarter). Counting those as single quarterly draws inflated the mean, t, Sharpe and the annualised return. That is why `FINDINGS.md` showed the same lagged book at **Sharpe 0.99** in the headline table and **0.95** in the layer table. **Fix:** `build_lagged.stats_qnorm()` — moments on the per-quarter contribution, cumulative/annualised on the **summed** window length. **Effect:** headline lagged gross **453.6 bps / 0.99 / 17.64% ann → 412.2 bps / 0.95 / 14.92% ann** over **12.3 years, not n/4 = 10.5**. The two tables now agree exactly. **Quote 0.95.** Layer, drop-idio and CAPM figures were already normalised and are unchanged.
- **🟢 All three are pinned by `tests/test_review_regressions.py`** (9 hermetic tests): the calendar-vs-trading-day offset, the entry floor for escalated books, and the equivalence of the two bases when every window is one quarter.

### Added 2026-09-07 (Pershing — confidential-treatment rows make a filer unstudiable)

- **🔴 `BW-RESTRICTED` confidential-treatment weight is the single best predictor of whether a filer can be studied at all — check it FIRST, before concentration and before spending on a returns fetch.** Pershing Square was run as a third filer precisely because it is the *most concentrated* book available (median effective N 3.3, vs Berkshire's 4.0), on the then-current rule of "pick by concentration". **It failed Stage 0 at 195 bps against a 75 bps stop.** The cause is not concentration and not the method: a large share of the disclosed book is not disclosed. Rows under SEC confidential treatment arrive with `ticker: None` / `security_id: "BW-RESTRICTED"` and have no market data at any price.

  | Filer | median restricted weight | max | Stage 0 | verdict |
  |---|---:|---:|---:|---|
  | Berkshire | **1.2%** | 6.3% | 61 bps | PASS |
  | D. E. Shaw | 16.9% | 44.4% | 78 bps | FAIL |
  | Pershing | **22.7%** | **100.0%** | 195 bps | FAIL |

  Pershing's 2013-12-31 book is **95.6% restricted by weight** (two hidden rows plus one visible 4% position), and it has quarters that are **100% restricted**. Coverage runs from an 83% median down to a **2.6% minimum**. **This is not a tunable threshold** — restricting to the best-covered quarters still fails (104 bps at ≥98% coverage, n=11). The one filer that passes the gate is the one whose book is essentially fully disclosed.
- **🟡 The correlation runs the wrong way.** The concentrated activist managers that look most attractive for a name-level rebuild are exactly the ones who trade through swaps and request confidential treatment. Concentration and studiability are *negatively* related in this sample. **Screen: one `get_filer_holdings` call, compute the share of book weight in rows with no ticker, treat >~10% as unstudiable.** This corrects the selection rule previously recorded in HANDOFF §9.
- **🟢 Pershing has no missing-book problem at all** — 52 of 52 teos back to the 2013 floor return a holdings snapshot with `report_date == teo`, unlike Berkshire's three stub rows. Its 27-ticker union across 13 years also confirms genuinely low name turnover. The book is clean; it is simply half-hidden.

### Added 2026-09-07 (project closeout — terminal-row defect, stub rows, teo reconciliation)

- **🔴 BUG: the TERMINAL row of `get_filer_portfolio` carries a forward return over an OPEN-ENDED window, not one quarter.** Every other row's return is the forward quarter `(teo, teo+1Q]`. The last row's is measured from `teo` to roughly the engine's data horizon. **Test used:** the market layer is ~SPY by construction, so compare each row's `portfolio_market_return` against SPY over that row's own forward quarter. Non-terminal rows agree to ~60 bps median; terminal rows deviate **2.7×–34×** that, and the horizon that would reproduce them is never one quarter:

  | filer | terminal teo | dev vs SPY | × median | implied horizon |
  |---|---|---:|---:|---:|
  | Berkshire | 2025-12-31 | +1242 bps | 21× | 1.9 quarters |
  | Greenlight | 2023-12-31 | +4146 bps | 34× | **9.2 quarters** |
  | Appaloosa | 2026-03-31 | +790 bps | 7× | 0.7 quarters |
  | D. E. Shaw | 2026-03-31 | +262 bps | 5× | 0.7 quarters |
  | Pershing | 2026-03-31 | +130 bps | 3× | 0.7 quarters |

  Greenlight is decisive: its last filing is 2.5 years stale and its "one quarter" return matches SPY over **9.2 quarters** — consistent with all terminal rows ending at the same calendar horizon regardless of their teo. **Consequence: drop the terminal row from any quarter-aligned analysis.** Including Berkshire's pushed its Stage 0 gate from **61 bps (PASS) to 84 bps (STOP)** on the strength of one row, and it contaminated the endpoint-based 46-quarter layer Sharpes. **Worth raising with the API team** — we can detect and drop it, but not fix it upstream.
- **🔴 The three Berkshire "missing-book" quarters are STUB ROWS, not missing books.** 2014-09-30, 2020-09-30 and 2025-03-31 carry a `portfolio_gross_return` but no holdings snapshot — because the rows describe a portfolio of **one or two names**: `n_holdings_active` 1/1/2 and `total_aum_usd` $620M / $386M / **$885K**, against a **$73.4B** median for the 42 real quarters (0.845% / 0.526% / **0.001%**). `get_filer_holdings(as_of=X)` correctly falls back to the prior quarter's ORIGINAL because there is no full book behind the row. **Not recoverable by any `as_of` escalation or `amendment_type` filter, and not worth recovering.** Their drop-idio returns average **837 bps/q vs 372** for real quarters — which is the entire A→B step of the Sharpe bridge, so the 46-quarter 1.003 is *contaminated*, not merely sample-selected.
- **🟡 CORRECTION to the 2026-07-27 "teo series has calendar gaps" note.** Full Berkshire reconciliation: `get_filer_portfolio` returns **50 rows**; **46** carry a `portfolio_gross_return`; **43** have a matching holdings book; minus the terminal row = **42 usable**. Of the four teos previously called "missing" (2015-06-30, 2021-06-30, 2023-09-30, 2023-12-31), only **2021-06-30** is genuinely absent from the series — the other three are **present as rows but carry a null `portfolio_gross_return`**, as does 2013-06-30. The practical advice is unchanged (use `teo + 3 months`, never "the next teo in the series"), but the characterisation was imprecise.
- **🟢 Lesson generalised (second time).** Both bugs found in this project — NaN poisoning and the terminal row — were cases where a *plausible-looking* value flowed through a pipeline that never checked it against an independent quantity. The cheap defence in both cases was the same: compare against something the model already implies (coverage-vs-value for NaN; the market layer vs SPY for the terminal row). **Build that cross-check into any new endpoint consumer.**

### Added 2026-08-17 (NaN-poisoning bug in the gross-return path — affects D.E.Shaw AND Berkshire)

- **🔴 BUG (fixed): `build_lagged.window_return` compounded `∏(1+r)` WITHOUT dropping NaN return days, so one bad name nulled an entire quarter.** A name with a single NaN return day in the window returns NaN (not None), which still counted toward `covered` in `portfolio_window_return` but poisoned the weighted sum → the whole portfolio window went NaN. Smoking gun: D.E.Shaw 2013-09-30, ticker `Z` (Zillow, freshly IPO'd, all 10 window-days NaN), **weight 0.03%**, nulled the entire quarter. The decomposition path (`name_layer_windows`) already dropped NaN days; the gross path did not — an inconsistency. **Fix:** drop NaN days before compounding, skip all-NaN names (→ None); plus a defensive `isnan(R)` guard in `portfolio_window_return`.
- **⚠️ This bug SILENTLY DROPPED QUARTERS and moved published results materially — the exact "dropped-for-a-data-reason" trap Conrad flagged on the Berkshire Sharpe.**
  - **D.E.Shaw report-date study:** dropped **13 of 49** quarters (all 2013–2017, the weak early half). Fixed → n=49. The headline **flipped**: post-report-vs-control paired t **2.86 → 1.15 (significance lost; 1.22 at 82% cov, 1.15 at full 93%)**; the effect is now beta (regression α t=−0.64, β=1.29), not special. The buggy 36-quarter sample had isolated the strong recent years.
  - **Berkshire lagged backtest (prior, already-audited deliverable):** the same shared `window_return` dropped **7 windows** — Stage 1 n **35 → 42**, lagged gross Sharpe **0.85 → 0.99**, mean 415.8 → 453.6 bps/q. **The prior Berkshire numbers were DEFLATED by this bug.** This needed a dedicated Berkshire re-run + re-audit (LAGGED_RESULTS.md, attribution_audit.xlsx) — since completed; current numbers are in FINDINGS.md. **NOT silently rewritten here** — flagged for review because it reopens presented figures.
- **🟢 Lesson generalised:** any pipeline that renormalises to "covered" weight must treat NaN the same as missing. Coverage looking healthy (e.g. 68%) is not proof the window computed — a NaN name inflates `covered` while nulling the return. Always check the returned value, not just the coverage.

### Added 2026-08-17 (D.E.Shaw report-date window study — history floors, coverage, layer validation)

- **🟡 The studiable history is capped by the DAILY-RETURNS floor (2013-07-29), NOT by holdings or filings.** D.E.Shaw's `get_filer_portfolio` series runs **81 quarters back to 2005-12-31**, and holdings snapshots with `report_date == teo` exist back to **2013-09-30** (all 31 older books 2013–2021 are present, report_date matches, zero missing-book gaps — the only DEShaw missing-book quarters are recent: 2023-12-31, 2024-03-31). But `get_ticker_returns` has no data before **2013-07-29** and `get_returns_decomposition` none before **2011-07-27**, so any post-report-window measurement is floored at 2013. **Net: ~13 studiable years (49 quarters, 2013-09-30 → 2026-03-31), not the 20 requested.** The binding constraint is returns, so no amount of holdings/portfolio history helps.
- **⚠️ D.E.Shaw layer decomposition FAILS validation again — the idiosyncratic layer will not reproduce.** Reproducing the endpoint's own unlagged quarterly layer returns for D.E.Shaw (covered-name renormalised): market mean|diff| ~50bps (median 28), sector ~24 (17), subsector ~12 (10), **idiosyncratic ~102 (median 73) — well over the 50bps bar.** Same failure mode as the lagged-backtest Stage 0 (79bps): high turnover (~22%/q) + thin coverage means the name-level residual (the arithmetic remainder, hence the most coverage-sensitive layer) can't be rebuilt from the covered subset. **Consequence: no D.E.Shaw factor split (market vs sector vs selection) can be published from a partial-universe rebuild.** The market layer is least coverage-sensitive and roughly reproduces; the idio layer is the one that breaks. Extending the cache to the top-92%-weight union across all 49 studiable books required fetching ~767 additional names (returns+decomp, ~$46) and lifts median covered weight from ~82% to **~93%** (min 75%). Even at 93% the idiosyncratic layer still fails validation (median 59bps) — the residual is too coverage-sensitive to rebuild. Every windowed result must renormalise to the covered book and state coverage.
- **🟢 Report-date window primitive (trading-day offsets after `teo`) works cleanly on cached data.** Anchor = last trading day ≤ report_date; windows [+d_start..+d_end] in trading days map to `(start, end]` date bounds fed to the existing `portfolio_window_return` / `portfolio_window_layers` helpers. Quarter-ends are often non-trading days (e.g. 2023-09-30 Sat) — anchoring to the last trading day ≤ teo handles this without special-casing.

### Added 2026-08-03 (audit session — amendment fields, synthetic filing dates)

- **🟡 Filing dates look CONSTRUCTED, not observed — the "45-day lag" is largely a default.** `filing_date − teo` is **exactly 45 days for 63–68% of periods across all five filers** (Berkshire 63%, Pershing 63%, Appaloosa 68%, Greenlight 67%, D.E.Shaw 65%); the remainder are almost all 46–48 (a report_date+45-day figure rolled to the next business day). Four *independent* managers do not file exactly on the deadline 65% of the time — this is a computed `report_date + 45 business-day` placeholder, not measured filing timestamps. **Consequence: "45 days is real" overstates it — the median-45 result measures the §13(f) deadline convention baked into the data, not observed filing behaviour.** The ~35% "other" values (and the amendment tail) are the only genuinely observed variation. Separately, `search_filers` metadata exposes `filing_date_source: "placeholder_lag_75d"` — a *different, cruder* +75-day placeholder (report+75; e.g. Berkshire 2025-12-31 → 2026-03-16) that we do NOT use; our portfolio/holdings dates use the +45 convention. **Neither the portfolio nor the holdings response carries a `filing_date_source` flag** — only `search_filers` does, so we cannot tell per-row which dates are observed vs defaulted.
- **🟢 Amendment fields exist and are historical (corrects the "no form_type" note).** `get_filer_holdings` envelope carries `filing_type` ("13F-HR"), `amendment_type` ("ORIGINAL"), `accession_number` on both current and historical vintages. `get_filer_holdings(as_of=X)` resolves to the ORIGINAL book on/before X, so its `filing_date` is the clean original — unlike the portfolio endpoint's `filing_date`, which is amendment-contaminated for a minority of teos. Filtering to ORIGINAL removes the >90d lag tail (Berkshire max 228→~48).
- **⚠️ The 3 "missing-book" quarters do NOT resolve via the amendment filter.** For Berkshire 2014-09-30 / 2020-09-30 / 2025-03-31, no ORIGINAL (or any) holdings snapshot with report_date == teo exists in the store — `as_of` returns the prior quarter's ORIGINAL. This is a genuine holdings-coverage gap, independent of amendments. D.E.Shaw has the same pattern (e.g. no 2023-09-30 book).

### Added 2026-07-27 (lagged-backtest build — daily name-level rebuild)

- **🔴 Some `teo`s have a `portfolio_gross_return` but NO holdings snapshot.** For Berkshire, `get_filer_holdings(as_of=X)` never returns report_date == teo for **2014-09-30, 2020-09-30, 2025-03-31** — even at as_of = teo+120d it returns the *prior* quarter's book. Yet `get_filer_portfolio` carries a gross return for those teos. So the two endpoints disagree on which quarters exist. These quarters cannot be rebuilt from holdings; a daily name-level backtest must detect (report_date != teo) and exclude or carry the prior book. 3 of 46 for Berkshire.
- **🔴 The `get_filer_portfolio` `teo` series has calendar gaps.** Berkshire is missing **2015-06-30, 2021-06-30, 2023-09-30, 2023-12-31** entirely. A backtest that sets each window's end to "the next teo in the series" silently doubles those windows (produced a −600 bps rebuild artifact). The forward return is one *calendar* quarter — use `teo + 3 months`, not the next available teo.

### Added 2026-07-26 (reporting-lag / layer-attribution diagnosis)

- **🔴 `available_date` does NOT exist at all** (CORRECTED 2026-08-03). Earlier this entry said the holdings envelope carries a *null* `available_date` key — **that was wrong; there is no `available_date` or `availability_date` key on the portfolio rows or the holdings envelope.** Per the schema owner: `filing_date` is the canonical knowledge-time field for 13F; the `availability_date` spelling is used only on ETF/benchmark endpoints. `get_filer_portfolio` rows carry `teo` + `filing_date`; the `get_filer_holdings` envelope carries `report_date`, `filing_date`, `as_of_basis='filing_date'`, `filing_type`, `amendment_type`, `accession_number`. Use `filing_date` as the availability field; do not look for `available_date`.
- **⚠️ Per-quarter returns are aligned to `teo` (report date), NOT `filing_date`.** `portfolio_gross_return` at T is the forward return over (T, T+1Q], **starting at quarter-end**. The ~45-day reporting delay is therefore **not baked in** — the series implicitly assumes you hold the book from quarter-end, ~45 days before it is public. Any "point-in-time" claim on this series has a half-quarter of look-ahead per period.
- **Lag `filing_date − teo` is a hard ~45 days for all four filers.** Median = mode = 45 (the §13(f) deadline); no time drift (|corr with time| ≤ 0.23). Ranges: Berkshire 45–228 (n=50), Pershing 23–168 (n=80), Appaloosa 41–48 (n=40), Greenlight 44–114 (n=73). Outliers >90d are amendments; managers file at the wire. Pershing's min 23 (some early/amended filings) is the only sub-45 cluster.
- **Partial-quarter (filing_date → next teo) returns are NOT exposed.** The endpoint returns whole-quarter forward returns only; the (teo, filing_date] sub-window can't be subtracted. A lag-aware series entering at `filing_date` therefore cannot be built from `get_filer_portfolio` alone — it needs a daily name-level rebuild (`get_filer_holdings(as_of=filing_date)` × `get_ticker_returns`, chained from filing_date). A whole-quarter-lag proxy is cheap but measures a different question (re-attributes whole quarters; moves Berkshire layers <1 bp under low turnover).
- **Layer additivity is approximate, not exact.** `gross − Σ(market, sector, subsector, idio)` has mean +4.5 bps/q but median |residual| 33 bps and max |residual| 214 bps (`identity_residual` field is null). The means reconcile to gross within ~5 bps/q; per-quarter the layers miss by a signed ~33 bps that cancels. Treat the decomposition as a diagnostic attribution, not an identity.
